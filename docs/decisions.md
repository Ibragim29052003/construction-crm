# Решения и допущения

- Все постановщики работают в одной компании, видят и редактируют общие данные. Отдельных организаций в ТЗ нет.
- У задачи один исполнитель, обязательно с ролью `executor`. Автор и дата создания не меняются при редактировании. Постановщик может переназначить или перенести задачу на другой объект без сброса статуса.
- Доработка возможна только после проверки и с непустым комментарием. Принятая задача — конечное состояние, повторное открытие не добавлял.
- История начинается с создания задачи. В неё входят смены статуса, а не изменения описания или исполнителя. После переназначения старый исполнитель теряет доступ к задаче и её истории.
- Удаление мягкое, с подтверждением: объект и его задачи исчезают из списков, но записи и история остаются в базе. Только постановщик может отметить данные удалёнными. Через API нельзя стереть журнал или вернуть удалённую запись; отдельный экран корзины не добавлял. Так одновременно соблюдаются требования об удалении задач и сохранности истории.
- Пользователи и роли создаются администратором в Supabase. В интерфейсе нет регистрации и управления пользователями.
- Запись идёт через RPC — функции базы. Прямые INSERT/UPDATE/DELETE закрыты для обеих ролей. Поэтому нельзя обойти проверку переходов или подменить автора истории. Функции выполняются с правами владельца, используют пустой `search_path` и сначала проверяют действующего пользователя. [Supabase Advisor](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable) предупреждает о доступных `SECURITY DEFINER`-функциях: здесь это намеренные точки записи, проверенные негативными тестами.
- Для создания используется постоянный UUID формы; смена статуса получает отдельный ключ запроса. Повтор того же запроса не добавляет запись в историю. Изменения и удаления проверяют версию записи. Повтор редактирования после потерянного ответа может вернуть конфликт — для этого сценария достаточно обновить данные.
- RTK Query хранит серверные данные в кеше и обновляет затронутые выборки после записи. Нет периодического опроса; данные перечитываются при возврате фокуса или восстановлении соединения. При смене аккаунта кеш очищается.
- Для небольшой демонстрационной базы фильтрация и поиск локальные. При большом количестве записей понадобятся серверная пагинация и поиск: сейчас действует стандартный лимит Supabase на выдачу (1000 строк), включая вложенные выборки. Realtime, уведомления, вложения и сроки задач за рамками задания.
- Для доступности используются обычные кнопки, подписи полей, фокус с клавиатуры, текстовые статусы и системные модальные окна с удержанием фокуса. Есть мобильная раскладка и режим уменьшения анимации.

Все обязательные сценарии реализованы. Отдельный сервер не понадобился: авторизация, правила доступа и транзакции находятся в Supabase. Пароли демонстрационных пользователей в репозиторий не включены.
